# architecture (방법론·패턴 고려 메뉴)

"이럴 땐 이런 걸 **고려해볼 수 있다**"를 **큐레이션된 메뉴**로 제시한다. **비처방** — 하나를 강요하지 않고, 상황에 맞는 후보 + **언제 적합/언제 아님**을 보여줘 **네가 고르게** 한다. LLM 기본지식과 차별점 = 큐레이션·"고려 트리거"·유저 선호·안티패턴 경고.

## 2레벨 메뉴
| 레벨 | 무엇 | 정본 |
|---|---|---|
| **① 방법론·아키텍처 스타일** | 프로세스·구조 수준 (TDD·DDD·클린/헥사고날·CQRS·이벤트드리븐·SOLID·12-factor) | `references/methodologies.md` |
| **② 디자인 패턴** | 코드 수준 해법 (GoF 생성·구조·행위 + 동시성·통합) + **안티패턴** | `references/patterns.md` |

## 규율 (비처방)
- **"고려 가능" 제시만** — 강요 X. 각 후보에 **언제 적합 / 언제 아님(오남용)**.
- **패턴 위한 패턴 금지** — 문제 없는데 패턴 끼워넣지 않는다. 단순함이 이긴다.
- 유저 선호·프로젝트 맥락 반영. 불확실하면 "확인 필요".

## 도식 (선호 반영 — `diagram` 위임)
- **선택 결정흐름**("이 상황이면 이거 고려")은 **mermaid `flowchart`(결정트리)**로, **패턴 구조**는 **`classDiagram`**로 그려 보여준다. → 작도는 **`diagram`에 위임**(mermaid 정본). references엔 예시 도식.
- **적응적** — 흐름·구조·비교면 도식, 단순하면 텍스트(도식 범벅 금지). [[feedback_prefer-diagrams]]

## 선택 후 라우팅
- 방법론 **실행**은 odin 실행스킬 소프트의존: TDD=`odin:test-driven` · 타입주도=`odin:type-driven` · 계약=`odin:design-by-contract` · 증명=`odin:proof-driven` · 검증우선=`odin:validation-first`. 있으면 그걸로, 없으면 「수행」가 그 방식으로.
- 설계 반영=`architecture`(plan 기록) · 구현=「수행」.

## 경계
- 여기 = **후보 메뉴**다. 실제 **설계 결정**은 백본의 「계획」 단계가, **현행 파악**은 알아내기 profile, **검수**는 `review`가 한다 — 셋이 여길 소환해 후보를 참고한다.
