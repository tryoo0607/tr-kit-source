# frontend-request — 요청서 양식·필드 가이드

표 중심. 각 변경은 **브레이킹·FE영향·조치**를 반드시 채운다. 깊이(간단/상세/패치)에 따라 §2·§4를 넣고 뺀다.

## 변경 구분 (taxonomy)
| 구분 | 의미 | FE 시사 |
|---|---|---|
| **추가** | 신규 엔드포인트/필드 | 새 호출·바인딩 구현 (보통 비브레이킹) |
| **변경** | 아래 하위 종류 중 하나↓ | 기존 코드 수정 (브레이킹 가능) |
| **삭제** | 엔드포인트/필드 제거·deprecated | 호출 제거·대체 (대개 브레이킹) |

**"변경" 하위 종류 (닫힌 목록)** — 요약표 "변경 내용"에 어느 것인지 태그:
`요청 스키마` · `응답 스키마` · `상태코드` · `인증/권한` · `에러 형식`

> **브레이킹** = FE를 안 고치면 **깨지는가**(런타임 에러·화면 오작동). 판단해서 표에 Y/N.

## 요청서 양식

```markdown
# FE 변경 요청서 — <제목>

| 항목 | 값 |
|---|---|
| 관련 티켓/PR | <링크> |
| BE 변경 요약 | <1줄> |
| 작성일 | <YYYY-MM-DD> |
| 긴급도 | 낮음 / 보통 / 높음 |
| 브레이킹 포함 | 예 / 아니오 |
| 배포 순서 | BE 먼저 / 동시 / FE 먼저(또는 feature flag) |
| 담당(BE) | <이름/연락> |

## 1. 변경 요약
| # | 구분 | 엔드포인트/대상 | 변경 내용 | FE 영향(화면·모듈) | 브레이킹 | FE 조치 |
|---|---|---|---|---|---|---|
| 1 | 변경 | `GET /users/{id}` | 응답에 `nickname` 추가 | 프로필 화면 | N | 필드 바인딩 추가 |
| 2 | 추가 | `POST /auth/verify` | 신규 | 인증 플로우 | - | 신규 호출 구현 |
| 3 | 삭제 | `GET /legacy/foo` | 제거(deprecated) | 목록 X | Y | 호출 제거·대체 |

## 2. 상세 (변경별)   ← [상세]·[패치] 깊이에서만
### [1] `GET /users/{id}` — 응답 필드 추가
- **Before → After** (스키마 diff)
  ```diff
    {
      "id": 1,
  +   "nickname": "string"
    }
  ```
- **상태코드/에러**: 변화 없음 (또는 새 4xx/5xx 명시)
- **인증/권한**: 변화 없음 (또는 헤더·스코프 변화)
- **예시**
  ```sh
  curl -H "Authorization: Bearer <t>" https://api/users/1
  # 200 → { "id":1, "nickname":"길동" }
  ```

## 3. FE 조치 체크리스트
- [ ] [1] 프로필 화면 `nickname` 바인딩
- [ ] [2] 인증 플로우에 `POST /auth/verify` 연동
- [ ] [3] `GET /legacy/foo` 호출 제거 + 대체 경로

## 4. 제안 패치 (선택)   ← [패치] 깊이, FE 소스 볼 때만
> ⚠️ **제안**일 뿐 — 리뷰·적용은 FE(또는 「수행」). 자동 적용 아님.
- **산출물 = 별도 `changes.patch` 파일**(`git apply`/`git am` 가능한 기계 형식). 요청서 본문엔 **파일 포인터 + 변경 파일 요약**만(인라인 덤프 X).
  - 예: `→ changes.patch (3 files: ProfileView.tsx, api/user.ts, types.ts)`
- 소규모(1~2줄)면 인라인 스니펫으로 갈음 가능.

## 참고
- API 문서(OpenAPI/Swagger) · BE PR · 관련 이슈 링크
```

## 필드 가이드 (권장 채움)
- **브레이킹** — 가장 중요. Y면 배포 순서·마이그레이션 명시.
- **배포 순서** — 브레이킹이면 보통 **FE 먼저 배포 or feature flag**로 무중단. 비브레이킹이면 동시/무관.
- **예시 payload** — 실제 request/response 샘플. FE가 스펙 대조·목킹에 바로 씀.
- **상태코드·에러·인증** — 응답 200만 보지 말 것. 새 에러 코드·에러 바디 형식·헤더 변화는 FE 예외처리에 직결.
- **FE 영향(화면·모듈)** — 어느 화면/컴포넌트가 닿는지. 모르면 "확인 필요"로 남기고 추정 금지(근거 규율).

## 소스 도출 팁 (BE diff → 변경표)
- **엔드포인트**: 라우터/컨트롤러 애노테이션 diff(`@GetMapping` 등 추가·삭제·경로 변경).
- **스키마**: DTO/response 모델 필드 추가·삭제·타입 변경.
- **OpenAPI/Swagger** 파일 있으면 그 diff가 가장 정확 → 우선 참조.
- 도출 불확실하면 표에 **"확인 필요"** 표기(사실인 척 금지).
