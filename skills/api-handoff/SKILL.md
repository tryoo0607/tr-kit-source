# api-handoff (BE→FE 변경 요청서)

백엔드 변경으로 **프론트 반영이 필요할 때**, FE 팀이 바로 읽고 조치할 수 있는 **표 중심 정형 요청서**를 산출한다. API 스펙 변경/추가/삭제, 상태코드·에러·인증 변화 등을 "무엇이 바뀌었고 / FE에 어떤 영향이고 / 뭘 해야 하는가"로 정리. **정본 = `references/template.md`**(양식·필드 가이드).

> BE→FE가 1차 대상이지만 **API 소비자 일반**(모바일·타 서비스)에도 그대로 쓴다.

## 입력 (2경로)
| 경로 | 방식 |
|---|---|
| **수동 나열** | 유저가 "이 API 바뀜/추가/삭제" 말로 → 표로 정리 |
| **소스 도출**(권장) | BE **diff·PR·branch**를 읽고 변경 API를 **자동 추출**(controller·OpenAPI/Swagger·DTO 변화) |

## 깊이 (3단계 — 요청 시 지정, 기본=간단)
| 모드 | 담는 것 | 언제 |
|---|---|---|
| **간단**(기본) | 헤더 + 변경요약표 + FE 조치 체크리스트 | 빠른 핸드오프 |
| **상세** | + 변경별 before/after 스펙·예시 payload(curl/JSON)·에러/상태코드/인증 변화 | 변경 크거나 브레이킹 |
| **패치** | + **별도 `changes.patch` 파일**(FE 소스 보고 산출, 요청서엔 포인터) | FE repo도 볼 때 |

## 산출 흐름
1. 입력 파악(수동 or BE diff 도출) + 깊이 확인(안 물으면 간단).
2. `references/template.md` 양식으로 요청서 작성 — **표 우선**, 각 변경에 **브레이킹 여부·FE 영향·조치** 필수.
3. **브레이킹/롤아웃** 판단 — FE 안 고치면 깨지는지, 배포 순서(BE먼저/동시/FE먼저·flag).
4. 상세면 before/after·예시 payload, 패치면 **별도 `changes.patch` 파일**까지(요청서엔 포인터).
5. 산출물 위치 확인 — 요청서(md)는 대화 출력·파일·사용자가 지정한 문서 시스템, 패치는 `changes.patch` 파일.

## 소프트의존/위임
- 🔑 **여긴 산출(제안)까지다.** 제안 patch를 실제로 적용하는 건 FE 쪽 일이다 — 리뷰를 거쳐야 한다.
- 문서 톤·서식 일반 규약은 `convention`.

## 경계
- 여기 = **BE→FE 변경 전달용 핸드오프 문서**(표 중심, 조치 지향). 일반 코드·제품 문서(README·docstring) 관례는 `convention`.
- 회사 프로젝트면 project-local 양식이 있으면 그걸 우선(tr-work 규칙) — 없으면 이 양식.
