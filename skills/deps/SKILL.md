# deps

**의존성 관리** — 추가·업그레이드·제거·취약점 audit. **리포트 먼저(영향도 포함) → 이행할 것 확인 → 진행.** 자동으로 올리지 않는다.

## 흐름 (report-first)
1. **조사/audit** → **리포트**: 무엇을 바꿀 수 있나(outdated·취약) + **breaking 여부**(changelog) + **영향받는 기능/사용처(impact)** + 재테스트 대상.
2. **이행할 것 확인** — 무엇을 바꿀지 사용자 선택(업글은 특히 묶어서 자동 X).
3. **승인분만 실행** — 설치·업글 **명령은 유저 실행/안내**(시스템·네트워크). → **검증**(`test`, 영향처 위주).

## 영향도 분석 (impact) ⭐
- 변경 대상 라이브러리를 **어디서 쓰나 추적**(import·호출 검색, 알아내기 profile 연계) → **영향받는 기능·모듈** 목록.
- breaking이면 그 사용처가 어떻게 깨지는지 → **재테스트 대상**으로(`test`·관련 `project` 소환).

## 작업 유형
| 작업 | 요지 |
|---|---|
| 추가 | 필요성·대안·라이선스·유지상태 검토 후(의존성=부채) |
| 업그레이드 | changelog·breaking 확인 → 영향처 재테스트 |
| audit | 취약점 점검(툴 감지→없으면 권장·설치 질문) |
| 제거 | 미사용 정리(영향도 확인 후) |

## 툴·소프트의존
- 패키지매니저는 **repo 것**(npm/pnpm·go mod·pip/poetry·cargo…) 감지·사용, lockfile 존중.
- **odin:deps-upgrade**·audit 툴(`govulncheck`·`npm audit`·`pip-audit`) 있으면 활용, 없으면 감지→설치 질문.

## 경계
- 영향처 파악=알아내기 profile / 검증=`test` / 커밋=`git` / 취약점 심각시 blocker=`review`.
- 상세 = `references/managing.md`.
