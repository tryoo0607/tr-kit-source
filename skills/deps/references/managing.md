# 의존성 관리 (절차)

**항상 report-first.** 실행(설치·업글)은 확인 후, 명령은 유저가.

## 공통 — 영향도 분석 (변경 전 필수)
1. 대상 라이브러리 **사용처 추적**: import/호출을 검색(알아내기 profile 연계) → 어떤 기능·모듈이 쓰나.
2. **영향 범위** 산정: 직접 사용 + 간접(그 모듈을 쓰는 상위)까지.
3. → **재테스트 대상** 도출: `test`로 검증할 것, 관련 `project` 소환.
4. 리포트에 [변경·breaking·영향처·재테스트 대상] 묶어 제시 → 확인.

## 추가
- **정말 필요한가**(작은 유틸은 직접 구현이 나을 때). 대안 비교.
- 라이선스(프로젝트와 호환?)·유지상태(최근 릴리스·이슈·스타)·크기·전이 의존.
- lockfile 갱신, 최소 버전 명시.

## 업그레이드
- **changelog·마이그레이션 가이드** 확인 → breaking 목록화.
- **한 번에 하나(또는 관련 묶음)** — 문제 격리. patch/minor는 묶어도, major는 개별.
- 올린 뒤 **영향처 재테스트**(code-test). 실패 시 원인=디버그 지침.

## audit (취약점)
- 툴 감지(`govulncheck`·`npm audit`·`pip-audit`·`cargo audit`) → 없으면 권장·설치 질문(유저 실행).
- 결과 리포트: 심각도·영향 버전·수정 버전 → 업그레이드 계획으로.

## 제거
- **미사용 확인**(영향도 분석으로 실제 안 쓰는지) → 제거 → lockfile 갱신 → 테스트.

## 안전
- 실행 명령은 유저 안내(`! npm install ...` 등). lockfile·매니페스트 변경은 커밋(`git`).
