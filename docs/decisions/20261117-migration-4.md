# 4번 — BMAD·조사·설계·개발 연결 이관

## 범위와 근거

사용자의 “이후 일괄로 하면 되는 거면4번가고” 요청에 따라 scratch source에서 기존 기능 연결을 이관했다. 계획은 로컬 `_bmad-output/migration-4-20261117/plan.md`에 있다. 운영 설치·배포·공식 기능 업데이트·프로젝트 setup·실제 원격 작업은 수행하지 않는다.

남긴 상태를 구분한다. 실제 제품 지침 주입·hook 조합·공식 설치본 workflow 실행·압축/재개는 전체 연결 뒤 통합 검증 대상이다. Git 등록·기존 hook 체인·복구 관리기는 **미이관 기능**이며 검증만 남은 것으로 표시하지 않는다.

## 기능 배치와 책임

| 위치 | 책임·변경 |
| --- | --- |
| common/base/skills/bmad 및 bmad-* 28개 | 기존 사용자 진입점 이름·역할을 유지한 자체 연결. 공식 본문·템플릿·runtime은 동봉하지 않음 |
| bmad/references/connection.md | BMAD 계열의 고유 요구/기록·조사 근거 분리·조건부 전문 도구 연결 |
| common/base/skills/find-docs | 기존 선택 공식 Context7 CLI에 직접 연결. 외부 skill의 npx/버전 fallback 문구를 치환한 사본은 사용하지 않음 |
| common/base/skills/frontend-design | 공식 skill에 실제 brief·보존 범위·필요 결과 전달. 가상 고객 이력을 실제 요구로 승격하지 않음 |
| common/base/skills/playwright-cli | 기존 선택 공식 CLI·확인한 help로 직접 연결. session 소유·입출력/저장 경계·관측/기능 구분 유지 |
| common/base/references/external-connection.md | 위 wrapper들이 함께 쓰는 명시 provider 선택·공식 설치 근거·실패·원문 보호 계약의 단일 위치 |
| common/base/scripts/provider_links.py | 기존 조립 validator 재사용. 명시 ID·종류·제품의 entry pin만 읽기 전용으로 확인하는 resolve/CLI 추가 |
| common/base/scripts/dev-tools.toml | 기존 Context7 0.8.2·Playwright CLI0.1.22/engine tuple만 이관. 설치/업데이트 도구는 아님 |

공식 bmod-core-tools·bmod-method·bmod-toolsmith는 모듈 metadata여서 자체 실행 skill로 복제하지 않는다. 공식 설치 도구가 관리할 필수 metadata와 resources는 해당 공식 설치본 소유다. 자체 진입점을28개로 유지한 것은 원본 업무 절차를 자체 재구현했다는 뜻이 아니다. PTBMAF·Design Doc 전용 기능은 기존 README에서도 미구현 상태이므로 이번에 신규 도입하지 않았다.

## 기존 bindings와의 차이

- 기존 자체 runtime_note의 요구/정정·Sources/Constraints/Boundaries/Done 연결, 연구의 원문/추론 분류, 선택 전문 도구 연결을 자체 계약으로 보존했다.
- 공식 원문에 runtime_note를 append하거나 replacements를 적용하지 않는다. 원문·사본·resources를 kit에 동봉하지 않는다. 입력과 결과 대조에서 고유 정책을 적용하며 공식 절차를 교체하지 않는다.
- Context7와 Playwright는 **같은 기존 선택 공급자의 공식 CLI**를 직접 사용한다. 외부 skill의 설치 지시를 문구 치환한 뒤 원본을 그대로 적용했다고 보고하는 방식을 제거했다. CLI help/버전 정적 확인과 실제 조회·브라우저 실행은 구분한다.
- 공식 BMAD hub·개별 기능은 실제 공식 SKILL.md로 진입해야 한다. 내부 render/resolve/scripts와 root는 그 공식 지침에 따라 해석한다. `_bmad`/uv 부재나 HALT를 source 직접 실행·자동 설치로 우회하지 않는다.
- 공식 checkout의 origin·기존 선택 revision·clean 상태를 읽기 전용으로 대조했다. 이31개 entry는 원문 보호 검사 근거이며 **공식 설치 완료·native 실행 가능 증거가 아니다**. 구 kit의 동봉/치환 설치본을 새 공식 provider로 간주하지 않는다.
- entry SHA 일치는 해당 파일 pin 검증이다. source/version 문자열은 독립 인증이 아니며 공식 패키지/필수 resource·제품 지원·실제 실행 검증을 대체하지 않는다. 실제 host-local provider 등록과 공식 설치 근거는 통합 단계에서 연결해야 한다.

## 조립 배치 보완

1〜3의 source 상대 참조 검사는 통과했지만 당시 조립기는 skill만 root의 skills/로 옮겼다. 이 배치에서는 skill의 `../../scripts/...` 같은 source 상대 참조가 조립 결과에서 깨질 수 있었다. 4번의 교차 참조 확인에서 발견했으며 과거55개 조립 통과를 전체 참조 통과로 소급 변경하지 않는다.

현재 자체 source bundle은 `common/base/skills`, `common/base/scripts`, `common/base/references`를 유지한다. 공통 instructions/workflow도 source 위치를 보존하고, 생성된 root AGENTS/CLAUDE용 workflow만 동일 source에서 생성한다. 두 workflow는 따로 편집하는 기준 사본이 아니다. 새 자체 reference도 명시 inventory에 포함했다. 실제 조립 결과의 Markdown 상대 파일 링크를 양 제품에서 대조했다. **native 설치 가능한 plugin 구조는 아직 아니다.**

## 읽기·수행 흐름

```text
요청 → 수행자가 해당 자체 wrapper 읽기
     → BMAD이면 필요한 계열 연결·조건부 정책 적용
     → 공통 외부 연결 계약 적용
     → provider_links CLI로 명시 ID·종류·제품·현재 pin 확인
     → 공식 설치 근거·필수 resources·제품 지원 대조
       ├─ 부재/불일치: 외부 수행 보류, 가능한 입력/자료 분석 지속
       └─ 확인됨: 공식 SKILL.md 또는 CLI help로 진입
                 → 승인된 공식 수행 → 원래 요구·결과·검증 대조
```

지침 읽기·entry 확인·실제 공식 실행·제품 통합을 같은 단계로 표시하지 않는다. 선택하지 않은 provider를 파일시스템으로 탐색하지 않으며, 명시 선언 자체의 잘못된 shape/중복 identity는 오류로 남긴다.

## 감사·검증 범위

현재 source 형식·직접 실행·회귀·원문 gate·조립 및 입력/의존 부재 모델 사례의 근거와 남은 항목은 [검증](../verification.md)의 4번 항목을 참조한다. 저작/범위 대조는 동일 작성자, 모델 출력 평가는 별도 grader다. 모든31개 wrapper의 전체 공식 workflow·자동 발동을 모델 사례3개로 인증하지 않는다.
