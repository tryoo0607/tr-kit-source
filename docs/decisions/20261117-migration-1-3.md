# 1〜3 기능 묶음 이관

## 범위와 근거

사용자의 “1, 2, 3은 거진 문제 없을 것 같긴 한데 일단 진행” 요청에 따라 scratch에서 세 묶음을 이관한다. 작업 범위는 `_bmad-output/migration-1-3-20261117/plan.md`에 기록했다. 전체 기존 기능의 승계·운영 설치·배포·프로젝트 이동·원격 갱신 승인으로 확대하지 않는다. 세 묶음은 함께 검증할 단위이며 skill 역할을 하나로 합치는 기준이 아니다.

공통 요구의 정본은 기존 `_bmad-output/kit-principles-discussion-20261113.md`의 관련 절과 이후 사용자 정정이다. 이 문서는 현재 구현 위치·차이·검증을 연결하며 기존 원문 기록을 복제하지 않는다.

## 공통 지침과 제품 배치

- `common/base/instructions.md`는 최소 공통 원칙과 조건부 workflow 진입을 소유한다. `workflow.md`는 요구·결정 연결, 승인과 조회, 계획/외부 연결, 검수와 재개를 소유한다.
- `adapters/codex/AGENTS.md.template`, `adapters/claude/CLAUDE.md.template`은 공통 본문을 정확히 한 번 삽입한다. 별도 제품 정책 사본을 만들지 않는다.
- 생성 파일의 존재는 제품이 자동으로 주입했다는 증거가 아니다. 현재 조립 결과는 native 설치 가능한 plugin이 아닌 자체 source bundle이다.

## 공식 외부 연결과 조립

- `common/base/scripts/provider_links.py`는 명시 JSON 선언의 외부 entry 경로·SHA256 pin·제품 선택을 검증한다. `source`·`version`은 제출한 근거이며 pin 일치가 공식 출처 인증·실행 성공을 증명하지 않는다.
- JSON은 version=1, providers 배열이다. 각 항목은 id, kind(skill/cli), entry(절대 경로), products(codex/claude), sha256, source, version을 갖는다. 다른 제품 전용 항목은 unsupported이며 그 entry의 존재·실행을 검증했다고 표시하지 않는다. 선언과 host 절대 경로는 로컬 입력이고 kit source에 실제 호스트 값을 고정하지 않는다.
- `scripts/assemble.py --product PRODUCT --source-root ROOT --output NEW_OUTPUT --catalog CATALOG --scope SCOPE --providers PROVIDERS`는 자체 공통 파일과 선택 adapter만 새 외부 디렉터리에 쓴다. 외부 원문·바이너리·bindings/upstream 디렉터리는 동봉하지 않는다.
- 조립 전 fresh 원문 검사 → provider pin 확인 → 자체 목록/범위 확인 → 새 output 생성 → 실제 output 원문 검사 → source/provider 재대조 → 실제 output 전체 비밀 검사·정확한 파일 목록/bytes 재대조 순서다. 검사 실패는 CLI exit2로 반환하며 성공 결과를 내지 않는다.
- 실패한 output은 진단용으로 보존한다. `assembly.json`은 path·sha256 필드를 분리한 파일 목록이며 완료 인증서가 아니다. 경로를 JSON key로 사용한 체크섬 표현은 generic-api-key 오탐을 일으켜 필드 구조를 바꿨다. 비밀 검사 규칙·예외는 완화하지 않았다. 파일 존재·과거 통과로 후속 전송을 허용하지 않으며 전송 직전 현재 대상에 fresh 검사를 수행해야 한다. 실제 전송기·설치기는 아직 없다. 동시 OS 쓰기를 원자적으로 배제하는 격리 경계도 아니다.

## 기존 자체 기능의 이관과 차이

| 대상 | 이번 구성·보존 | 미이관·미검증 |
| --- | --- | --- |
| security-scan | 기존 자체 Semgrep/Trivy 연결, 새 Gitleaks/Git 검사 CLI·비활성 renderer에 맞춘 문서 | scanner 자동 설치, Git 등록·체인·복구 관리기. 실제 제품 native·활성 조합 |
| profile-setup | 자체 설정 schema·템플릿·수동/기존 parser 점검 절차 | 전용 의미 validator/resolver, 실제 설정 변경·소비자 지원 |
| project | group/repo/workspace 역할·배치·기존 공간 확인·도구 연결 | 실제 등록·이동·공간 생성 |
| session | 연속 작업·원문 조회·위임·진단·runtime 갱신 자체 script와 fixture 시험 | BMAD/document 후속 이관, 실제 사용자 창 조작·재시작·소비 확인 |
| orca-cli | 선택한 CLI의 버전 일치 `skills get` guide. receipt와 실제 응답 구분 | 실제 원격 요청·조율 실행 |
| worktrunk | 공식 설치 CLI의 해당 명령 도움말 참조로 변경 | 기존 upstream 문서/bindings는 가져오지 않음. 실제 worktree 변경 |
| orca-update | 대상 선택·순차 갱신·재접속·실제 버전/terminal probe 검증 계약 | 실제 업데이트·서비스 조작 |

출처 대조: `_bmad-output/migration-1-3-20261117/own-inputs.json`은 이관 전 자체 파일의 경로·hash다. 이관 수정과 검증의 최종 대상은 같은 폴더의 source manifest에서 구분한다. 기존 파일의 존재를 새 사용자 합의로 승격하지 않는다.

Git 정책의 `allow_artifacts`는 현재 engine에서 등록 항목 그대로 적용하며 `tr-local-docs` 저장소/허용 suffix를 강제하지 않는다. 자동 등록 기능을 이관할 때 이 제약을 구현·검사해야 한다. 보안 문서에 이를 숨기거나 기존 등록 관리기가 이미 제공되는 것으로 쓰지 않는다.

## 흐름과 검증 경계

```text
업무 요청 → agent가 담당 SKILL.md·선택 reference 읽기
         → 확인한 공식 CLI/설치본을 실행하거나 실제 자료 조회
         → 결과·receipt·완료/미결 대조

자체 source → assemble.py → 공통 fresh gate와 provider pin 검증
                       → 선택 제품의 자체 source bundle
                       → 실제 파일 원문·비밀 검사 → 성공/실패 반환
```

실제 검증 결과와 반복 범위는 [verification](../verification.md)의 이번 이관 항목에 기록한다. 공통 지침·script/합성 adapter·조립·새 모델 세션·제품 native·압축/재개를 서로 다른 증거로 다룬다.
