# 프로젝트 관리

작업할 코드 위치 확인, repo 연결과 group 구성, 독립 workspace 준비에 사용한다. 이 파일은 공통 업무 판단을 소유하고 도구 조작은 선택한 외부 wrapper가 소유한다.

## 입력과 전제

요청한 결과, 대상 repo/호스트, 확인된 경로와 기존 등록을 사용한다. 관계가 불명확하면 [구조의 대상과 관계](structure.md#대상과-관계), 신규 배치이면 [신규 배치 기준](structure.md#신규-배치-기준), 독립 공간이면 [workspace 기준](structure.md#workspace-기준)만 확인한다. 구조 검토만으로 도구를 실행하지 않는다.

## 수행 방법과 절차

### 위치 확인

1. 작업할 대상과 필요한 정보를 확인한다. 이미 제공된 실제 경로와 기존 정보로 충분하면 재사용한다.
2. 관리 등록의 경로나 workspace 목록이 필요할 때만 아래 도구 연결을 적용한다. 경로가 없거나 로컬 접근이 실패했다는 이유만으로 관리 조회로 전환하지 않는다.
3. 접근 가능한 checkout에서 Git 최상위 경로, .git의 디렉터리 또는 파일 유형, common dir, branch 또는 detached HEAD와 변경 상태를 읽기 전용으로 확인한다. 상위 Git에 속하는 폴더를 독립 repo로 분류하지 않는다. 경로와 symlink, worktree 연결도 대조하며 로컬 정보로 Orca 등록 상태를 추측하지 않는다. 다른 호스트는 허용된 접근 수단을 따른다.
4. 사용할 실제 경로, 확인한 근거와 부족한 정보를 반환한다. 불명확한 대상은 질문하고 비슷한 경로로 자동 대체하지 않는다.

### 연결과 공간 준비

1. 조회와 변경을 구분하고 기존 등록/공간을 먼저 확인한다. 동일 repo의 중복 등록이나 불필요한 workspace 생성을 피한다.
2. 요청한 등록/group 관계 또는 독립 공간의 필요, repo/시작 ref/호스트와 영향을 확인한다. 설정 변경은 본문의 configuration 분기로 연결하고 관리 등록 변경과 구분한다.
3. 아래 도구 연결로 요청된 조작만 수행한다. 도구의 실제 경로/생성 방식과 공통 구조가 충돌하면 조작 전에 차이를 알리고 해결한다.
4. 반환된 식별자, 관계, 실제 경로와 완료 상태를 검증한다. 조회 요청을 변경으로 확대하거나 새 공간을 현재 세션의 자동 이동으로 취급하지 않는다.

### 임시 프로젝트와 정식 전환

1. 구조 지침의 임시 배치와 정식 전환 기준으로 대상 경로, 기존 파일과 Git 상태를 확인한다. 신규 임시는 승인된 경로에 로컬 repo를 준비한다. 이미 Git repo이면 다시 초기화하지 않는다.
2. 원본 이동이면 연결 worktree, 미반영 변경, 실제 사용 중인 경로와 Orca 등록을 먼저 조회한다. 이동 대상과 영향을 제시하고 승인 범위를 확인한다. Worktrunk의 relocate를 원본 repo 전체 이동 명령으로 취급하지 않는다.
3. 확인된 Git 및 파일 조작 수단으로 요청된 초기화 또는 이동만 수행한다. 최초 commit이 필요하면 현재 승인과 Git 규칙을 확인한다. 임시 repo 준비를 원격 생성, push나 자동 worktree 생성으로 확대하지 않는다.
4. 초기화 후 repo 최상위 경로와 시작 상태를 확인한다. 이동 후에는 원본과 연결 worktree의 Git 접근, 필요한 설정 경로와 Orca 등록을 재확인한다. 설정 변경이 요청되면 [설정 연결](configuration.md)의 계약을 적용하고 요청된 등록 갱신은 아래 Orca 연결로 처리한다. 연결 검증을 완료하지 못하면 정식 전환 완료로 보고하지 않는다.

### 구조 전환과 의존성 검증

1. 최신 사용자 요구에서 호스트별 유지 목록, 보관과 삭제 범위, 이름 규칙, group, 임시와 worktree 배치를 확인한다. 위 위치 확인 절차와 [구조와 배치](structure.md)의 해당 기준으로 실제 Git 경계와 목표를 대조한다. 목록에 없거나 오래됐다는 이유만으로 삭제하거나 계속 사용할 것으로 결정하지 않는다. 이름 변경, archive, 사용 종료와 삭제는 다른 요청이다.
2. 실제 항목을 유지 프로젝트, 필요한 worktree, 보관 자료, 생성물과 제외 대상으로 구분한다. worktree의 미커밋 변경, 미병합 작업, 잠금과 사용 중인 세션을 확인한다. 필요한 항목만 유지하되 불명확한 변경을 버리거나 자동 병합하지 않는다.
3. 이동 전후 표에 실제 경로와 Git 경계, 현재와 목표 소속, 처리 이유, 연결된 소비자, 검증과 복구 방법을 넣는다. 사용자가 배치안을 먼저 보겠다고 한 경우 확정 전 이동하거나 예시 이름의 group을 생성하지 않는다. 기존 계획과 다른 요구는 계획에 반영하고 새 승인을 추정하지 않는다.
4. repo와 worktree 이동은 아래 Worktrunk 연결 및 확인된 Git 절차를 사용한다. .git 파일이나 common dir을 임의 편집하거나 일반 mv만으로 연결이 유지됐다고 판단하지 않는다. 원본 checkout과 연결 worktree의 이동 순서, 새 경로에서 접근 가능 여부를 대조한다.
5. 경로와 remote를 소비하는 백업, timer와 service, 배포 및 복구 실행기, symlink, BMAD 출력, 문서와 Orca 등록을 확인한다. 원격 저장소 이름 변경은 origin뿐 아니라 주소 검증 조건과 deploy key의 저장소 연결도 대조한다. 필요한 설정 작업은 configuration 연결, 호스트 실행은 해당 업무 담당에 맡기며 허용되지 않은 capability로 우회하지 않는다.
6. 승인된 범위만 반영하고 각 소비자를 새 위치에서 검증한다. 보호 사본과 기존 자동 작업이 있어도 복구 가능성이나 새 백업 성공을 대신하지 않는다. 백업 구조와 기록 작업은 document 연결로 대조한다. 충돌이나 실패 시 원본과 증거를 유지하고 관련 변경을 멈춘다.
7. 실제 전후 표와 검증 결과를 반환한다. 파일 이동, Git과 worktree 연결, 설정 반영, Orca 등록, 백업 및 복구 경로의 동작을 별도로 판정한다. 미검증이 남았으면 전체 전환 완료로 보고하지 않는다.

## 연계와 의존

| 대상 | 적용 조건 | 입력과 필요한 결과 | 의존과 부재 시 동작 |
|---|---|---|---|
| [worktrunk wrapper](../../worktrunk/SKILL.md) | 추가 worktree의 조회, 생성 또는 정리가 필요함 | 대상 repo/호스트, 요청 동작, 시작 ref와 브랜치, 경로와 승인 범위. 결과는 실제 경로, Git 연결과 완료/오류 상태 | 해당 조작에 필수. 부재/미지원은 보류하고 Orca 생성으로 자동 대체하지 않음 |
| [orca-cli wrapper](../../orca-cli/SKILL.md) | Orca가 관리하는 등록/소속/기존 공간 조회 또는 등록 변경이 필요함 | 요청 동작, 대상 repo/group/호스트, 실제 checkout 경로와 승인 범위. 결과는 식별자/관계/등록 경로/완료·오류 상태 | 해당 관리 조작에 필수. 부재/미지원은 해당 조작 보류. 기존 로컬 조회와 Worktrunk만 필요한 조작까지 중단하지 않음 |
| document | 구조 전환이 기록 위치나 백업 사본에 영향을 줌 | 기존 group/project 식별자와 실제 기록, 변경 범위, 소비자와 검증 필요사항. 결과는 소속과 경로 대조, 실제 반영과 미결 | 해당 기록 대조에 필수. 부재 시 관련 전환 완료 판단을 보류하며 자체 백업 규격을 만들지 않음 |

도구 선택과 요청 계약은 이 표, 도구 연결/조작은 wrapper가 소유한다. 선택한 SKILL.md를 읽고 필요한 명령 자료만 적용한다. 실제 에이전트 세션 생성과 전환은 session이 소유하며 등록 변경과 구분한다.

## 결과와 완료 판단

위치 확인은 실제 사용할 경로와 확인 범위가 구분된 상태다. 등록/group 변경은 재조회 관계가 요청과 일치해야 한다. 공간 준비는 비동기 완료와 실제 checkout/시작 상태 확인이 필요하다. 조작 요청 접수만으로 완료를 판단하지 않는다.

## 실패와 복구

경로 충돌, 도구 부재와 미지원은 해당 조작을 보류하고 근거를 알린다. 부분 생성과 비동기 실패는 현재 결과를 보존하고 자동 삭제/재생성하지 않는다. Git으로 공간을 생성해 관리 도구 등록을 대신하지 않는다.
