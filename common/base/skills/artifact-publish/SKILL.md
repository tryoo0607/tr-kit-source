# artifact-publish

## 목적과 역할 경계

- 업무 담당이 내용·근거·산출물의 정확성을, 이 skill이 승인된 표현·게시·접근 확인을 소유한다. 게시를 위해 사실·관계·미확인을 새로 확정하지 않는다.
- 파일 작성·로컬 미리보기 요청을 게시로 확대하지 않는다. 기존에 합의한 아티팩트/계정 전용 링크 요청은 그 범위로 진행하며 명령마다 재승인하지 않는다.

## 입력과 전제

- 완성본/정본·제목·기존 URL/ID·계정과 공유 범위·현재 제품·실제 kit root를 받는다. 새 페이지의 기본은 본인 전용이며 공개·초대·조직 공유 확대는 별도 범위다.
- 기존 페이지는 지정한 ID·소유권/편집 권한·현재 audience를 확인한다. 불명확하거나 요청과 충돌하면 그 변경만 보류한다. URL 추측·다른 계정/제품·nginx/Orca 공개 링크로 대체하지 않는다.

## 수행 방법과 절차

1. 완성본을 재사용하고 필요한 표현만 다듬는다. 여러 도표는 각각의 의미·탐색을 유지한다. 새 도표가 필요하면 아래 담당에 실제 근거·독자·형식만 전달한다. 일반 파일 초안이면 여기서 외부 게시 경로를 시작하지 않는다.
2. 현재 제품에 맞는 아래 adapter reference를 실제 kit root에서 읽는다. 두 제품 자료를 합치거나 공통 references/provider.md가 자동 생성된 것으로 가정하지 않는다. 자료/제품/게시 수단 부재는 파일을 보존하고 게시 미실행으로 알린다.
3. 실제 전송할 파일·패키지를 확정하고 security-scan의 선택 산출물 전송 검사를 적용한다. Git index 검사만으로 untracked HTML을 검사했다고 말하지 않는다. 결과/파일이 바뀌면 같은 실제 전송 범위로 재검사하며 실패·불완전 검사를 성공으로 취급하지 않는다. 패키징이 파일 집합을 바꾸면 확장된 실제 payload도 대조한다.
4. 적용 중인 호스트 고정 가드가 있으면 해당 규칙으로 docs.sync를 검사한다. capability 허용은 계정·내용·공유 범위의 승인이 아니다. DENY/실패를 다른 제품/호스트로 우회하지 않는다. 호스팅 인프라 변경은 별도 capability·승인 범위로 분리한다.
5. adapter가 연결한 공식 수단으로 게시하고 실제 URL·배포 상태·접근 범위를 대조한다. 가능한 경우 핵심 렌더·탐색을 확인한다. 생성·저장·배포·계정 보호·로그인 화면 렌더는 각각 판정한다.

## 제약과 주의점

- 로그인·조직 정책·native 승인·비밀 검사 실패를 우회하지 않는다. credential은 공식 수단이 정한 세션 메모리/입력 경계에서만 다루며 파일·명령 인자·회신에 복사하지 않는다. guard가 필수 credential 흐름을 막으면 충돌로 보고하고 검사 예외를 임의로 추가하지 않는다.
- 공식 도구가 로컬 파일 수정과 게시를 한 번에 수행한다면 그 수정도 승인 범위와 대조한다. 게시만 했다고 가정하거나 사용자의 정본 편집을 숨기지 않는다.

## 결과와 완료 판단

- 실제 반환 URL·공유 범위·게시 상태와 확인한 접근/렌더만 간결히 반환한다. 로컬 경로·예상 URL·인증 화면을 게시/본문 확인 성공으로 보고하지 않는다.
- 실패·timeout 뒤에는 같은 작업의 접수·version/deployment ID·상태를 확인하고 무조건 재전송하지 않는다. 부분 게시와 미확인을 보존한다.
