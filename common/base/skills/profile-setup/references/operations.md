# 설정 작업

설정 생성, 변경, 읽기 전용 점검/계획 또는 미지원 설계에 사용한다. 선택한 절과 공통 검사/완료/실패 기준만 적용한다.

## 입력과 전제

호스트, 요청 범위, 실제 선택 설정 파일과 소비자를 확인한다. [설정 해석 순서](config-schema.md#설정-해석-순서)로 관련 필드의 값과 출처를 확인한다. 경로 존재/접근은 확인하지만 폴더 생성, clone, 자료 이동이나 동기화를 실행하지 않는다.

## 수행 방법과 절차

### 읽기 전용 점검과 계획

1. 현재 설정의 문법, 필드와 지원 버전, 유효 경로/정책을 검사한다. 파일이 없으면 부재를 밝히고 필요한 설정 계획만 제시한다.
2. 등록/실경로와 충돌, 소비자의 지원 여부를 확인한다. unknown key와 미지원 계약을 임의로 해석하지 않는다.
3. 요청이 계획이면 대상 파일, 전후 값, 영향받는 소비자와 부족한 조건을 제시한다. 점검만 요청받으면 차이와 근거를 반환한다. 둘 다 파일 쓰기나 자동 복구를 하지 않는다.

### 생성과 변경

1. 현재 값과 요청 변경, 영향받는 소비자/공간/공유 범위를 대조한다. 구현 지원이 불명확한 필드는 변경을 보류하고 계획과 미결을 알린다.
2. 필요한 신규 파일은 [설정 템플릿](../assets/config.example.toml)의 승인된 필드만 사용한다. 기존 파일을 전체 템플릿으로 교체하지 않는다. 변경 대상과 전후 값, 영향을 먼저 제시하고 승인 범위가 이미 정해졌다면 재질문하지 않는다.
3. 쓰기 직전 현재 파일을 재확인해 다른 변경을 보존하고 승인된 항목만 수정한다. 기존의 유효한 소속 override와 무관한 설정을 유지한다. unknown key를 조용히 삭제해 정상화하지 않는다.
4. 아래 검사 범위로 저장된 값과 승인된 diff를 대조한다. 설정 저장과 소비자 반영을 구별하고 실제 공간/자료 이동을 대신 실행하지 않는다.

### 미지원 설정 설계

1. 필요한 의미, 현재 계약의 부족한 부분과 소비자 요구를 정리한다.
2. 새 필드와 해석/호환 영향은 제안으로 명시한다. 현 규격에 없는 필드를 실제 config에 적용하거나 다른 필드로 우회하지 않는다.
3. 계약 변경과 소비자 지원 검증이 준비될 때까지 해당 적용을 보류한다. 설계 검토 결과와 실행 미지원 범위를 반환한다.

### 검사 범위

문법 검사는 현재 사용 가능한 TOML parser로 수행한다. 의미 검사는 schema의 자료형/기본값/경로/정책 규칙과 실제 등록/파일 상태를 대조한다. 현재 확인된 전용 resolver/validator가 있으면 지원 범위 안에서 사용한다. 도구 이름과 실행 명령을 추측하거나 자동 설치하지 않는다.

전용 도구 부재 시 수동 대조와 문법 검사 결과를 명시한다. 문법 검사 수단도 없으면 문법 검증 미실행으로 보고하고 적용 검증 완료를 주장하지 않는다. 소비자의 실제 동작을 실행하지 않았다면 설정 검사 통과와 소비자 반영 미검증을 구분한다.

## 결과와 완료 판단

점검은 선택 파일, 확인한 유효 값/출처, 오류·충돌과 검사 범위가 명확하면 완료다. 계획/설계는 대상, 영향, 제안과 미지원 범위가 구분돼야 한다. 설정 파일 변경 완료는 승인된 diff와 저장값 일치이며, 검증 완료는 요청한 검사 범위의 통과 여부로 별도 보고한다. 수동 검사와 도구 검사를 혼동하지 않는다.

## 실패와 복구

파싱 오류, 설정/등록 충돌과 미지원 계약은 해당 변경 전에 해결한다. 쓰기 후 실패는 추가 변경을 멈추고 diff/영향을 알린다. 복구는 승인 범위에서 이번 변경만 대상으로 하고 다른 작업의 수정을 덮지 않는다. 외부 전송 실패를 저장소 재구성이나 자료 이동으로 자동 해결하지 않는다.
