# Hook 작성·수정

## 목적과 역할 경계

- hook의 목적·정책 근거, 검사 로직, 제품별 연결과 등록의 작성·수정 기준을 소유한다.
- 가드의 적용 범위와 hook이라는 실행 수단을 구분한다. hook이 사용자 정책이나 새로운 금지를 정하는 주체가 아니다.
- 공통 정책·승인·외부 재사용·조건부 시험은 진입점, 구체 도표·흐름·행동 시험법은 shared가 소유한다.
- 설치·신뢰 승인·등록 활성화·운영 적용은 설계·시험 대상과 실제 수행 권한을 구분한다. 이 문서를 읽거나 코드를 작성한 것만으로 활성화를 승인받은 것으로 판단하지 않는다.

## 입력과 전제

- 보호할 사용자 요구·금지·결정, 대상 행위, 적용 범위와 예외·변경 조건을 확인한다.
- 제품·버전·후보 이벤트·실제 payload와 결과 계약, 등록 source와 현재 활성 조합을 확인한다.
- 기존 hook·검사 도구·실행기의 책임과 재사용 범위를 확인한다. 비밀 검사 등 이미 담당 엔진이 있으면 같은 검사를 새로 구현하지 않는다.
- 코드·설정의 정적 확인, 공식 설명, 실제 native 이벤트 관측을 구분한다. 제품 계약이나 활성 상태가 미확인이면 임의의 필드·차단 효과를 설계 사실로 쓰지 않는다.

## 수행 방법과 절차

### 목적·적용 범위 설계

| 항목 | 명시할 내용 |
| --- | --- |
| 목적·근거 | 보호·확인할 대상과 요구·금지·결정의 기준 위치 |
| 적용 범위 | 전체 공통, 프로젝트 정책에 따라 판단, 특정 프로젝트 전용의 선택 이유 |
| 대상 행위 | 파일 쓰기·명령·커밋·전송 등 검사할 실제 동작 |
| 대상 식별 | 실제 저장소·경로·전송 대상의 확인 방법과 불명확한 경우 |
| 경계 | 비대상 행위, 허용에 포함되지 않는 추가 동작 |

- 공통 코드에 프로젝트 이름 목록을 넣는 방식으로 범위 구분을 대신하지 않는다. 프로젝트별 조건이 필요한 경우 정책 입력과 식별 방법을 설계한다.
- 현재 터미널 경로나 등록 위치만으로 대상을 단정하지 않는다. 다른 저장소를 지정한 명령·절대경로·경로 변환에서 실제 보호 대상을 확인한다.
- 식별할 수 없는 입력은 비대상이나 통과로 추정하지 않고 아래 검사 불가 정책에 연결한다.

### 검사 결과·실패 설계

| 검사 결과 | 실행 계약에 담을 의미 |
| --- | --- |
| 적용 대상 아님 | 이 검사의 범위 밖. 작업 전체의 허용 판정이 아님 |
| 통과 | 필요한 검사를 수행했고 해당 조건을 충족. 다른 권한·승인을 대신하지 않음 |
| 차단 | 금지·승인 범위 위반을 확인. 대상 동작 차단과 이유·근거 전달 |
| 검사 불가 | 입력·설정 부재, 식별 실패, 오류·시간 초과. 통과와 구분 |

- 검사 성격별 실패 정책을 사전에 정한다.
  - 실행 전 필수 보호 조건: 검사 불가이면 해당 동작 보류·차단과 원인 알림.
  - 참고용 점검·알림: 실패를 알리고 진행 가능. 점검 완료로 보고하지 않음.
  - 실행 후 검사: 이미 발생한 효과를 차단·복구한 것으로 판단하지 않고 실패·미검증을 알림.
- 필수·선택 설정을 구분하고 설정 부재로 보호 기능이 조용히 꺼지지 않게 한다.
- 재시도는 횟수·시간·중복 실행 위험과 중단 조건을 명시한다. 실행 중 임의로 필수 차단을 알림으로 낮추거나 우회 경로로 바꾸지 않는다.
- 공통 판정과 제품의 실제 처리 효과를 구분한다. 제품이 해당 이벤트에서 차단을 지원하는지, 오류·timeout을 어떻게 처리하는지는 확인된 계약과 native 시험으로 검증한다.

### 실행·중복 관계 설계

- 제품·설정 위치·이벤트·matcher·실행 명령·등록 범위와 담당 검사를 확인할 수 있게 연결한다. source 선언만으로 실제 활성 조합을 확정하지 않는다.
- 같은 요구의 검사 담당을 명시한다.
  - 같은 대상·시점·조건의 중복은 통합·등록 제거를 검토하되 기존 hook을 임의로 끄지 않는다.
  - 목적이 같아도 보호 시점이 다르면 각각 필요한지 판단하고 이유를 기록한다.
  - 범위가 다르면 보완 관계와 공통 로직의 재사용을 명시한다.
- 순서·결과 전달이 보장된 근거가 없으면 앞 hook의 가공 결과에 의존하지 않는다.
- 동시에 실행되거나 재호출됐을 때 파일·상태·외부 요청·수집·로그에 중복·충돌이 발생하는지 확인한다.
- 한 검사의 통과가 다른 검사의 차단·실패를 상쇄하지 않도록 제품의 결과 결합 계약을 확인한다.
- 마스킹 후 저장 같은 보호는 순서가 미보장인 별도 hook에 맡겨 안전하다고 주장하지 않는다. 저장 담당도 안전한 입력을 취급하도록 설계한다.

### 설정·예외·변경 권한 설계

- 기존 금지마다 대상·적용 범위·변경 조건·변경 권한을 명시한다. 별도 금지 체계를 새로 만들지 않는다.
- 작업 승인·프로젝트 설정·원칙 개정을 구분한다. 일반 작업 승인을 공통 금지 해제나 검사 비활성화로 확대하지 않는다.
- 공통·프로젝트·호스트 값의 소유 위치, 지원 항목·자료형·허용 값·기본값·필수 여부와 결합·충돌 처리를 정의한다.
- 프로젝트·호스트 값이 공통 금지를 자동 완화하지 않게 한다. 예외를 허용한다고 정하지 않은 규칙에 에이전트가 예외를 만들지 않는다.
- 사용자에게 명시적 변경 권한이 있어도 제품의 실행 권한을 대신하지 않는다. 파일 쓰기 가능성과 정책 변경 승인을 구분한다.
- 에이전트가 수정할 수 있는 자연어·설정·hook만으로 우회 불가능한 통제라고 주장하지 않는다. 실제 강제 경계와 남는 한계를 명시한다.

### 검증·추적 설계

- 요구의 기준 위치에서 공통 검사·제품 adapter·등록 설정·시험·결과를 찾아갈 수 있게 연결한다.
- 공통 로직, 제품별 입력·결과 변환, 실제 등록·trust·callback·차단·비대상 비간섭과 조합 시험을 구분한다.
- 정상·위반·비대상·경계 입력·필수 설정 부재·오류·timeout·재호출·동시 실행의 기대 동작을 정의한다. 관련 없는 사례는 비대상 근거를 남긴다.
- 소스·등록·제품 계약 변경의 영향받는 시험을 재실행한다. 이전 버전의 결과를 자동 재사용하거나 모든 작은 변경에 무조건 전체 시험을 강제하지 않는다.

## 연계와 의존

- 공통 검사 로직은 common/base/scripts, 제품 이벤트·입출력·호출 차이는 adapters/<product>/scripts, 제품별 등록은 adapters/<product>/hooks에서 소유한다.
- 실제 adapter는 공통 검사에 어떤 입력을 전달하고 어떤 결과를 제품 계약으로 변환할지 명시한다. 공유할 수 없는 제품 고유 처리는 adapter에 둔다.
- 제품·버전의 공식 문서·실제 메시지를 근거로 계약을 확인한다. 문서에 적힌 보장과 직접 관측한 효과를 구분한다.
- 기존 엔진·도구 연결은 식별자·버전·입력·결과·필수 여부·부재 동작을 실제 사용하는 쪽에서 소유한다. 코드 복사나 새 범용 위임기로 연결을 대신하지 않는다.

## 결과와 완료 판단

- 공통 보고에 검사 목적·범위·실패 정책·변경 조건, 실제 공통/제품별 배치와 등록 연결을 포함한다.
- 같은 폴더의 audit.md에 요구·정책·변경 파일·제품 계약·기존 hook 목록·실제 시험 증거·미검증을 전달한다.
- script 단독 결과, 설정 파일 존재, 설치 목록, trust, 실제 callback·차단은 각각 구분한다. 설계·합성 시험만 수행했다면 native 검증 완료로 표현하지 않는다.
- 작성·수정의 검증과 감사 보완은 진입점 기준을 따른다. 실제 활성화·운영 적용을 저작 완료의 자동 후속으로 수행하지 않는다.
