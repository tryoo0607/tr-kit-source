# BMAD 공식 설치본 연결

## 목적과 역할 경계

- BMAD 계열 자체 진입점의 공통 연결과 kit 고유 요구·도구 연결을 소유한다. 공식 기능의 본문·메뉴·단계·렌더러·상태 저장 형식은 여기서 다시 규정하지 않는다.
- 공통은 이 계열 wrapper를 사용할 때 읽으며 조건부 절은 필요한 것만 추가로 적용한다. 선택하지 않은 다른 BMAD skill 본문을 전부 읽지 않는다.

## 입력과 전제

- 호출 wrapper가 지정한 외부 연결 ID, 입력·필요 결과, 현재 제품·실제 프로젝트 cwd와 기존 요구/상태를 받는다.
- 공식 `bmod-*` 모듈 metadata는 설치 도구가 관리하며 실행 wrapper를 만들지 않는다. 모듈 설치·기능 지원 여부는 공식 hub/설치 근거로 확인한다.

## 수행 방법과 절차

1. [외부 연결 계약](../../../references/external-connection.md)의 전체 공통 절차를 적용한다. kit root·host-local 선언·product·호출 ID·종류 skill로 entry를 확인하고 그 공식 SKILL.md로 진입한다.
2. 실제 프로젝트와 공식 skill root를 구분해 공식 지침이 요구한 실행만 수행한다. 렌더가 필요한 기능은 공식 렌더 결과로 이어가며 workflow 원문을 직접 실행하거나 kit에 복제하지 않는다. 필요한 `_bmad`/uv 부재나 HALT/오류는 공식 실패 계약대로 보고한다. setup이나 새 initiative 생성이 필요한 경우 이번 승인 범위에 포함되는지 확인하며 자동 설치·초기화로 해결하지 않는다.
3. 기존 요구·금지·최신 정정·승인 범위·완료 기준을 작업 입력으로 전달한다. 공식 단계 전환·렌더 뒤에도 결과와 대조하되 runtime_note를 원문에 append하거나 별도 상태 정본을 만들지 않는다.
4. 필요한 경우 아래 조건부 절을 적용하고 공식 결과·실제 증거를 호출 wrapper의 완료 기준과 대조한다.

### 요구·기록 연결 — 요구 생성·수정·구현·검증에 적용

- 공통 workflow의 [요구·결정과 연결](../../../workflow.md#요구결정과-연결)에서 관련 조건만 적용한다. 기존 ticket·계획·source/companion과 최신 정정을 재사용하고 별도 대화 원장을 만들지 않는다.
- 요구 정본을 소유한 PO/PRD/brief 등은 실제 원문 locator·필요 발췌와 해석/결정을 구분한다. URI·세션 ID를 파일 경로로 사용하거나 확인하지 못한 원문을 요약으로 복원하지 않는다. 공식 memlog/기록 성공과 derived 문서 갱신 순서 및 필요한 독립 검수 회신을 유지한다.
- build는 ticket/계획의 Constraints·Boundaries·Done when과 필요한 companion을 소비한다. 구현자가 모든 source/대화를 재독하거나 의도 인터뷰를 반복하게 만들지 않는다. 의미 변경·정정은 요구 담당과 해결하고 요구 ticket을 임의 수정하지 않는다.
- 결과에서는 요구 ID/완료 기준과 실제 변경·검증·미실행을 대조한다. 문서 자체의 존재·기록 명령 성공을 독립 검수나 실제 실행 성공으로 대체하지 않는다.

### 조사 근거 — 조사·외부 조사 prompt·검증자에게 적용

- 공식 조사 기능의 firewall과 증거 요구를 유지한다. 기존 프로젝트 주장은 조사 질문의 맥락이며 그 자체로 외부 사실의 증거가 아니다.
- 공식 문서·해당 버전 소스·원 논문·직접 관측을 우선하고 원문 사실/출처 작성자 주장/자체 `[추론]`/미확인을 구분한다. 중요한 주장 가까이에 출처와 필요한 버전·시점을 남긴다. 재인용을 독립 출처로 세지 않는다.
- 분리 조사자·검증자 brief와 외부 Draft에도 이 고유 구분을 전달하고 digest/Process/요약/시각화까지 보존한다. 전달 승인·자료 범위를 확대하거나 전체 프로젝트 원문을 자동 수집하지 않는다.
- 커뮤니티 경험은 실제 읽은 글의 범위·시점에 한정한 보조 근거다. 인기 글 하나를 전체 사용자 의견으로 일반화하지 않는다. 얇은 자료·원문 미확인은 한계로 보고한다.

### 선택적 전문 도구 — 해당 필요가 있을 때만 적용

| 필요한 업무 | 연결할 담당과 전달 입력 | 필요한 결과·부재 시 동작 |
| --- | --- | --- |
| 특정 버전 API·기술 문서 | find-docs: 제품/라이브러리·정확한 버전·구체 질문 | 원문 근거·버전 불일치·미확인. 부재 시 현재 허용된 공식 문서/소스 조회 가능 범위를 확인 |
| 화면 시각 설계·제작 | frontend-design: 실제 brief·기존 시스템·스타일·범위 | UI 결과·디자인 근거. 부재 시 해당 전문 연결 미실행 |
| 실제 UI 동작/렌더 검증 | playwright-cli: URL·시나리오·viewport·소유 session·허용 저장 범위 | 실제 assertion/관측·오류·산출물. 부재 시 정적 검토와 실행 미실행을 구분 |
| 보안 검사 | security-scan: 변경 대상·목적·허용 범위 | 발견·오류·제외·검사 범위. 부재 시 해당 검증 미실행 |
| 설명용 구조/업무 시각화 | archify 또는 diagram-design: 실제 근거/데이터·독자·형식 | 도표와 검증·생략. 후속 이관 전에는 연결 부재로 표시하고 텍스트 설명 가능 범위 유지 |
| 문서 공동 작성 보완 | doc-coauthoring: 기존 정본·독자·설명 깊이·보존 요구 | 수정·독자 검토. 선택 기능 부재가 원래 업무 전체의 중단 사유는 아님 |
| Android/Wear 전문 판단·시험 | 실제 필요에 맞는 기존 Android/Wear 담당: pinned 버전·구조·시나리오 | 근거·변경·실행/미실행. 후속 이관 전 부재를 숨기거나 전 도구 순회를 강제하지 않음 |

- 대상의 실제 SKILL.md로 진입하고 그 내부 자료 경로를 호출자가 고정하지 않는다. 위 연결은 별도 agent·자동 실행을 보장하지 않는다.
- 필요하지 않은 담당을 기본 로드하지 않는다. 이미 충분한 근거·도구 결과는 재사용한다. BMAD가 자기 업무의 분석·문서·검증을 소유하며 README·자료 보관·게시 등 별도 업무는 해당 담당에 연결한다.

## 결과와 완료 판단

- wrapper 입력·공식 기능 반환·실제 산출물/검증·최신 정정과 완료 기준을 대조한다. 설치·렌더·도구 실행·모델 준수의 증거를 구분한다.
- 공식 지원과 kit 연결 차이·미실행·미확인을 숨기지 않는다. 지침 전달만으로 격리 조사자까지 정책이 소비됐다고 판정하지 않는다.

## 실패와 복구

- 공식 지침과 사용자 고정 제약의 실제 충돌은 해당 동작만 보류·보고한다. 원문 편집·절차 교체·우회 실행으로 해결하지 않는다.
- setup/HALT/오류·접근 거부는 확인된 상태를 보존하고 해당 공식 실패 절차를 따른다. 설치나 권한을 임의 확대하지 않는다.
