# 「계획」 상세

*(추출원: 구 `architecture`의 설계 접근 — **절차라서** 스킬에서 여기로 왔다)*

## 절차

1. **입력 확인** — 「정의」에서 확정된 요구. 불명확하면 계획을 짜기 전에 정의로 돌아간다.
2. **제약 파악** — 기존 아키텍처·패턴·기술스택·성능/보안 요구·마감. 제약에 **맞춰서** 설계한다.
3. **옵션 도출** — 후보 2~3개. 각각의 트레이드오프(단순성·성능·확장성·위험·공수).
4. **선택 + 근거** — 요구·제약에 비춰 하나를 고르고 **왜**를 남긴다.
5. **구체화** — 컴포넌트 책임 · 인터페이스 · 데이터 모델 · 경계 · 에러/엣지 처리 방향.
6. **작업 분해** — 구현 스텝(순서·의존).

## 🔑 산출에 **버린 대안**이 들어간다

고른 것만 적으면 다음 사람(과 세션)이 **같은 후보를 다시 검토한다.** 왜 안 골랐는지가 결정의 절반이다.

```markdown
| 결정 | 근거 | 버린 대안 |
|---|---|---|
| systemd unit으로 | 기존 방식과 일관 | cron — 상태 추적이 안 됨 |
```

작업을 넘는 결정이면 `decisions.md`에 `D-nnn`으로.

## 원칙

- **가장 단순한 것부터.** 요구 밖 확장 금지 — 과설계는 되돌리기 비용을 미리 내는 것이다.
- **기존 패턴 일관성이 우선.** 새 패러다임은 근거가 있을 때만.
- 🔑 **가역성으로 속도를 가른다** — 되돌리기 쉬운 결정은 빠르게, 어려운 결정(스키마·공개 API·데이터 마이그레이션)은 신중히. **이건 profile의 임계값과 같은 축**이다.

## 도식이 필요하면

Mermaid로 컴포넌트·흐름. **정본은 텍스트(git)** — 이미지로 굳히지 않는다. 갱신은 델타 편집(노드 ID 유지). 작도법은 `diagram` 스킬.
