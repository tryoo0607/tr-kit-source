# 판정하기

**산출이 평가다** — 코드 리뷰 · PR 리뷰 · 문서 검수 · kit 감사 · 코딩테스트 채점.

| | |
|---|---|
| **단계** | 진입 → 정의 → **수행(`ask(N)`)** → 마무리 (**계획·점검 스킵**) |
| **임계** | **높음** |
| **점검 관점** | — (**수행이 곧 판정**이라 별도 점검이 없다) |
| **수행 `runner`** | 🔑 **`ask(N)`** — 관점을 갈라 서브에게 |

## 독트린

> 🔑 **커버리지 우선 — 놓치지 마라. 걸러내기는 다음 단계다.**

*(추출원: R1 · R3의 code-review 교훈)*

리뷰의 실패 모드는 **놓치는 것**이지 과하게 지적하는 게 아니다. 먼저 넓게 잡고, 그 다음 리뷰어 게이트가 거른다.

## `ask(N)` — 관점을 격리한다

한 서브에게 *"보안·성능·누락 다 봐줘"* 하면 관점이 서로 오염된다.

```
수행 · ask(3)
  ├─ 서브1: 보안 관점으로만
  ├─ 서브2: 성능 관점으로만
  └─ 서브3: 요구 대비 누락 관점으로만
       ↓
  리뷰어 게이트 — 세 목록을 가정과 대조해 거른다
```

**서브는 파일을 안 고친다.** 말(지적 목록)만 돌려받으므로 충돌이 없다 — 멀티에이전트를 써도 안전한 칸이다.

## 리뷰어 게이트

서브가 낸 지적을 그대로 내보내지 않는다. **가정과 대조해서** 거른다:

| 거른다 | 남긴다 |
|---|---|
| 요구 밖의 지적 | 요구 안에서 실제로 깨지는 것 |
| 서브가 못 본 맥락 때문에 나온 오탐 | 재현 가능한 것 |
| 취향 | 근거가 있는 것 |

지적에 **severity**(`nit` / `concern` / `blocker`)를 붙인다.

## 왜 계획·점검을 스킵하나

- **계획** — 무엇을 볼지가 「정의」와 관점 목록에서 끝난다.
- **점검** — 수행 자체가 판정이다. 이중 판정은 리뷰어 게이트가 한다.
