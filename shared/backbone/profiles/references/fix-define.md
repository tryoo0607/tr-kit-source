# 「정의」 — 개선요청 변형

> 고치기 profile. *"뭘 개선하나"*가 모호할 때.


"성능 개선 필요", "이거 느려", "리팩터로 개선" 같은 **큰 개선요청**용 특수 케이스. 일반 breakdown(요구·질문·결정)에 **개선 특유 절차**(방법 탐색·단계 분류·지표)를 얹는다. (구 INBOX P1-2 "개선 접근 방법론" 흡수.)

## 절차
```
1. 요구 확인        — 무엇을 개선? 목표는? (막연 "빠르게" → 정량 목표로)
2. 현행 측정        — 추측 최적화 금지. 먼저 재보고 병목 특정 (code-perf 위임)
3. 개선방법 탐색     — 후보 여러 개 (각 효과·비용·리스크)
4. 작업 단계 분류    — 1차(큰효과·저위험) / 2차 / … 로 나눔
5. 지표 기록        — before/after 정량 (목표 vs 실측)
```

## 일반 breakdown과의 접점
| breakdown 렌즈 | 개선 변형에서 |
|---|---|
| 1 요구 | **정량 목표**로 (막연한 개선 → 수치) |
| 2 질문 | 목표·허용범위·측정법 확인 |
| 3 결정 | 개선방법 후보 중 택 (효과/비용 tradeoff) |
| 4 진행 | **단계 분류**(1차/2차) 로 나눠 진행 |
| 5 결과 | **지표 before/after** 표 |

## 위임 (§9)
- 측정·병목 = **`perf`**(측정 먼저, 추측 최적화 금지). 설계 = `architecture`. 구현 = 「수행」.
- 지표 정량 추적(before/after)은 **「계획」의 전후비교** — 목표·before·after·delta 표. improvement의 ⑤결과 지표를 그리로.

## 규율
- **측정 없는 최적화 금지** — 2번(현행 측정) 건너뛰지 않는다.
- 단계 분류는 **효과·위험 순** — 큰효과·저위험을 1차로.
- 지표는 **목표(선언) + 실측(검증)** 둘 다. 근거 규율: 실측 없으면 "확인 필요".
