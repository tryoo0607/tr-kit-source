# 안전 개선 — 영향조사 · 전후비교 · 회귀

> `fix.md` 독트린 *"사이드이펙트 0"*의 실행 지침.


> code-improve ③PLAN·⑤검증의 요리. 목표 = **부작용0, 딱 원하는 것만.**

## 영향조사 (blast radius) — ③에서 필수
고칠 대상이 **무엇에 닿는지** 먼저 조사(고치기 전):
- **역참조**: 이 함수/타입/필드를 **부르는 곳** 전부 (grep/LSP references). 시그니처 바뀌면 다 영향.
- **의존 방향**: 이게 의존하는 것 + 이걸 의존하는 것(양방향).
- **암묵 계약**: 공개 API·직렬화 포맷·DB 스키마·이벤트 — 바꾸면 외부 깨짐.
- **테스트 커버리지**: 이 경로를 덮는 테스트가 있나(없으면 ⑤ 전에 회귀케이스부터).
- 산출 = **영향 목록**(파일·심볼·위험도). 넓으면 `ask(N)`으로 다관점 조사.

## 전후 비교법 — ③에서 계획, ⑤에서 실측
"개선 됐나 + 안 깨졌나" 둘 다 측정 방법을 **PLAN에 미리** 세운다:
| 축 | 방법 |
|---|---|
| **개선 효과** | 목표 지표의 **before/after**(속도·복잡도·중복·커버리지). 기록에 표로 남긴다 |
| **회귀(안 깨짐)** | 기존 테스트 전부 green 유지 + 영향목록 경로 스팟체크 |
| **동작 동일성** | 리팩터면 입출력 동일 확인(골든 테스트·스냅샷·diff) |
- before를 **수정 전에** 캡처(안 하면 비교 불가).

## 회귀 케이스 — ③에서 확보
- 영향목록 중 **테스트 없는 경로**는 수정 전 `project`/`test`로 케이스 먼저(회귀 방지망).
- 버그 개선이면 **그 버그 재현 케이스**를 먼저(고치면 green 되게).

## 외과적 수정 규율 — ④
- **딱 그 변경만.** "김에 이것도" 금지 — 별건이면 별 항목으로 분리(다시 ①로).
- 단계적이면 **1커밋=1개선**, 매 단계 후 테스트 green 확인.
- 포맷·정리 섞지 마(diff 오염 → 리뷰·회귀추적 어려움).

## 편차 처리
- 수정 중 "영향이 예상보다 큼/딴 게 깨짐" → **멈추고 보고 → ②확인게이트로 복귀**. 계획 몰래 안 바꿈(guard 규율).

## advisor 최종 견제 — ⑤
- `review`로 "부작용 놓쳤나·성급 완료·검증 없이 done?" 자문. **blocker면 완료 아님.**

# 리팩터 (동작보존 구조 개선)

**겉보기 동작을 바꾸지 않고** 내부 구조만 개선한다.

## 원칙
- **동작 보존**: 기능 변경·버그 수정과 **섞지 않는다**(별도 커밋). 리팩터 커밋은 `refactor:` 타입.
- **테스트를 방패로**: 리팩터 전 기존 테스트 통과 확인 → 리팩터 → 다시 통과. 테스트 없으면 `test`로 먼저 특성화 테스트(characterization) 확보 고려.
- **작은 스텝**: 이름 바꾸기·추출·인라인 등 작은 변환을 단계적으로. 매 스텝 검증.

## 흔한 대상
- 중복 제거(DRY) · 큰 함수/클래스 분해 · 네이밍 개선 · 조건 단순화 · 결합도↓.
- **과도한 리팩터 경계**: 요구·범위 밖으로 번지지 않게(`requirements` 범위 존중).

## 마무리
- 동작 동일 확인(테스트/수동), 결과는 project `exec`에 기록.
- 리뷰=`review`, 커밋=`git`.

# 디버그 (버그 원인 추적)

**증상이 아니라 근본원인**을 고친다.

## 절차
1. **재현** — 안정적으로 재현하는 최소 조건/입력 확보. 재현 안 되면 로그·상태부터.
2. **격리** — 범위를 좁힌다: 최근 변경(`git bisect`)·이분탐색·로그·가설검증. 한 번에 한 변수.
3. **근본원인** — 왜 그런지 설명 가능해질 때까지. 증상만 덮는 수정 금지.
4. **수정** — 원인을 고치고, 부작용·인접 케이스 확인.
5. **케이스화** — 이 버그를 **`project`에 등록**(+ expand로 유사 입력) → 회귀 방지.

## 원칙
- **추정보다 관찰**: 로그/디버거/실제 값으로 확인. 로그 수집·분석은 `logs` 스킬(재료 제공).
- 재현 불가한 것을 "고쳤다" 단정하지 않는다.
- odin debugging 워크플로 있으면 활용(소프트의존).
