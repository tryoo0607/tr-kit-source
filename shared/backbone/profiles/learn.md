# 알아내기

**산출이 이해다** — 기술 조사 · 학습 · 코드 파악 · 레퍼런스 분석 · 쇼핑 비교 · 스펙 확인.

| | |
|---|---|
| **단계** | 진입 → 정의 → **수행** → 마무리 (**계획·점검 스킵**) |
| **임계** | **높음** — 거의 안 묻는다 |
| **점검 관점** | — (스킵) |
| **수행 `runner`** | `inline` 기본. 넓은 조사면 `ask(N)` — **관점을 갈라서** |

## 독트린

> 🔑 **실측 없으면 기록하지 않는다.**

*(추출원: 구 `dig` — 이 profile로 흡수됨)*

조사의 실패 모드는 *"그럴듯한데 확인 안 한 것"*을 결론에 섞는 것이다. 추측은 **"확인 필요"로 명시**하고 사실과 섞지 않는다.

## 「수행」 지침 — 두 갈래

**산출이 누구의 이해냐**로 갈린다. 나머지(스킵 단계·임계·독트린·점검 관점)는 같다.

| | 조사형 | 문답형 |
|---|---|---|
| 산출 | **내가 이해한 것의 기록** | **유저의 이해** |
| 수단 | 파일·문서·실측, `ask(N)` | 대화 왕복 |
| 끝 | 실측이 모였을 때 | **유저가 자기 말로 정확히 되짚었을 때** |
| 기록 | `exec/` · `out/` | **기본 안 남긴다** (남길지는 유저가 정한다) |

### 조사형 — Start Wide

> 확장 5축 · 재현 실험 = `references/dig.md`

**넓고 짧게 시작해 좁힌다.** 처음부터 한 곳을 깊게 파면 엉뚱한 데를 팔 위험이 크다.

```
넓게 훑기 (여러 각도, 짧게)  →  어디가 답인지 보이면  →  거기만 깊게
```

여러 각도가 필요하면 `ask(N)`으로 **각 서브에게 서로 다른 검색 축**을 준다(컨테이너별 · 내용별 · 시간별 등). 한 서브가 여러 축을 맡으면 축이 서로 오염된다.

### 문답형 — 되짚기 루프

```
답한다  →  유저가 자기 말로 되짚는다  →  틀린 만큼만 교정한다  →  수렴
```

🔑 **되짚은 걸 그냥 "맞습니다" 하지 않는다.** 절반만 맞으면 **절반만 맞다고** 한다.
동의가 편하다는 이유로 넘어가면 유저는 틀린 이해를 굳힌 채 나간다 — 이 갈래의 유일한 실패 모드다.

- **비유는 조정 가능한 도구다.** 안 맞으면 새 걸 만들지 말고 **버린다**. 비유를 지키려다 사실을 비튼다.
- **틀린 전제를 먼저 잡는다.** 용어를 잘못 쓰고 있으면 그것부터 — 그 위에 쌓으면 다 무너진다.
- 내가 앞서 모호하게 말한 게 원인이면 **그렇다고 말한다.** 유저 탓으로 두지 않는다.
- **끝은 유저가 정한다.** 내가 "이제 이해했겠지"로 닫지 않는다.

> 조사형과 달리 **파일을 안 뒤져도 된다.** 다만 독트린은 그대로다 — 대화 중에도
> 단정할 사실이 나오면 **실측하거나 "확인 필요"로 표시**한다.

## 왜 계획·점검을 스킵하나

- **계획** — 무엇을 알아낼지가 「정의」에서 끝난다. 조사 경로는 알아가며 정해진다(미리 계획하면 틀린 계획을 고수하게 된다).
- **점검** — 산출이 이해라서 별도 검증 대상이 없다. 검증은 **독트린**(실측)이 수행 안에서 한다.

## 메모

산출물이 독립 문서면 `out/<slug>/`에 낸다. 기록(`exec/<slug>.md`)과 다른 것이다.
