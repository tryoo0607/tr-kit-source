# profile — 백본 위의 설정

**가르는 축은 도메인이 아니라 "작업의 모양"이다.** 코드/노션/홈랩/쇼핑으로 나누면 옛 `core/me/work` 구분과 같은 실수를 반복한다.

**profile을 실제로 다르게 만드는 건 넷뿐:**

1. 어느 **단계를 스킵**하나
2. **되돌리기 비용 임계값** (얼마나 묻나)
3. **독트린** (무엇이 좋은 산출인가)
4. **점검 관점 목록** (= `ask(N)`의 N)

> **두 작업이 이 넷에 같은 답을 내면 같은 profile이다** — 도메인이 달라도.
> 예: *노션 정리*와 *영어 학습 정리*는 넷이 전부 같다 → 같은 profile.

## 5개

| profile | 언제 | 계획 | 점검 | 임계 | 점검 관점 (N) |
|---|---|---|---|---|---|
| [**만들기**](make.md) | 없던 걸 새로 만든다 — 기능개발 · 문서 · 스킬/프롬프트 저작 | ✅ | ✅ | 중간 (10분) | 요구 충족 · 엣지케이스 · 테스트 **(3)** |
| [**고치기**](fix.md) | 있는 걸 바꾼다 — 버그수정 · 개선 · 리팩터 | ✅ | ✅ | 중간 | 회귀 위험 · 범위 이탈 **(2)** |
| [**알아내기**](learn.md) | 산출이 **이해**다 — 조사 · 학습 · 코드 파악 · 비교(쇼핑) | ⏭ | ⏭ | **높음** | — |
| [**되살리기**](restore.md) | 깨진 걸 복구한다 — 장애대응 | ⏭ | ✅ | **매우 높음** | 복구됐나 · 재발 방지 **(2)** |
| [**판정하기**](judge.md) | 산출이 **평가**다 — 리뷰 · 검수 · 감사 | ⏭ | — | 높음 | (수행이 곧 판정) |

## 단계 배치

```
만들기 · 고치기   진입 → 정의 → 계획 → [수행 ⇄ 점검] → 마무리
알아내기          진입 → 정의 ─────────→ 수행 ───────→ 마무리
되살리기          진입 → 정의 ─────────→ [수행 ⇄ 점검] → 마무리
판정하기          진입 → 정의 ─────────→ 수행(ask N) ─→ 마무리
```

## 「진입」 트리거

| 신호 | profile |
|---|---|
| *만들어줘* · *작성해줘* · *추가해줘* · 없던 것 | 만들기 |
| *고쳐줘* · *안 돼* · *개선* · *리팩터* · 있는 것을 바꿈 | 고치기 |
| *뭐야* · *어떻게 돼* · *조사* · *비교* · 산출이 이해 | 알아내기 |
| *죽었어* · *장애* · *복구* · 돌던 게 안 돎 | 되살리기 |
| *리뷰* · *검수* · *봐줘* · *평가* · 산출이 판정 | 판정하기 |

**애매하면 묻는다** — profile 오판은 절차 전체를 틀리게 하므로 임계를 넘는다.

## profile ↔ skill

**profile = 절차(모양) · skill = 도메인 지식.** N:M이다.

> 스킬이 담은 게 *절차*면 profile로 흡수(스킬 소멸), *지식*이면 남긴다, 둘 다면 쪼갠다.

## 영역(scope)과 직교한다

profile = **무엇을** 하는가 / 영역 = **어디서** 하는가. 회사에서 만들기, 오픈소스에서 고치기 다 가능. → `../../scopes/`
